# Hermes 委派工作流

> 分工：**Claude Code = 架构 / 出题 / 验收**，**Hermes = 具体编码**。
> 目的：把大 token 的实现工作分流给本机 Hermes，Claude Code 只做需要全局上下文和判断力的部分。

## 为什么需要规格书

Hermes 每次都是**冷启动**：不知道项目背景、不知道我们的约定、看不到历史对话。
所以不能说"帮我写个模板"，必须给一份**能独立执行的规格书**。

实测教训：让 Hermes 读一个模板文件报告占位符，它报了 6 个变量，实际只有 2 个——**它会臆测**。
所以规格书里凡是契约性的事实（变量名、路径、命名规则），**必须由 Claude Code 先核实再写死**，不能让 Hermes 自己去猜。

## 规格书模板

新任务放在 `docs/tasks/HERMES-<任务名>.md`，包含七个部分：

| 部分 | 作用 | 常见坑 |
|---|---|---|
| **背景** | 它需要知道的前提（为什么做这件事） | 省略会导致它做出"技术上对、方向上错"的东西 |
| **目标** | 一句话说清要什么 | |
| **交付物** | 精确到文件路径 | 不写死路径它会乱放 |
| **硬性要求** | 命名规则、契约、禁止引入的依赖 | **契约必须先核实**（见上文教训） |
| **视觉/行为规格** | 具体到颜色、尺寸、字体 | 写模糊了它会自由发挥 |
| **验收标准** | Claude Code 会逐条验的清单 | 让它自己也能自测 |
| **不要做的事** | 明确禁区 | 不写它会顺手改别的文件、自己 commit |

结尾固定加一句：**不要自己 commit，由 Claude Code 验收后统一提交。**

## 调用方式

```bash
~/.hermes/hermes-agent/venv/bin/python -m hermes_cli.main -z "严格执行规格书:<绝对路径>

<关键约束重申 2-3 条>

完成后报告:<你要它汇报什么>"
```

- 长任务会超时转后台，正常，等通知即可
- 先用一个小问题做**连通性测试**（例如"读这个文件报告 X"），确认它能读到项目文件再派正式活
- 当前 Hermes 用免费模型，慢；嫌慢可切 Groq 付费版（见 memory: hermes-service-ops）

## 验收清单（Claude Code 执行，不可省）

1. `git status --short` —— 确认**只**动了规格书允许的文件，没有越界修改
2. 逐条对照规格书的"验收标准"实测（不能只看 Hermes 的自我汇报）
3. 跑全量测试 `python3 -m pytest tests/ -q`，不得低于当前基线
4. 抽查关键契约（命名前缀、变量名、无外部依赖）——**这是 Hermes 最容易出错的地方**
5. 通过后由 Claude Code 提交，commit message 注明由 Hermes 实现

## 适合 / 不适合派给 Hermes

**适合**：模板/样式文件、重复性改造、按明确规格写独立模块、批量文本处理、文档撰写。

**不适合**：需要全局架构判断的重构、涉及多模块联动的改动、调试疑难 bug（需要反复试错和上下文）、
任何"需要先搞清楚现状再决定怎么做"的任务——这类 Claude Code 自己做更快更稳。
